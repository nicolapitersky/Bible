## How Claude Code Reads This Handbook

Claude Code reads instruction files in a defined hierarchy. Understanding this
hierarchy is essential — the wrong file in the wrong place is silently ignored.

### The Four-Layer Hierarchy

```
Layer 1 (lowest priority):  ~/.claude/CLAUDE.md        — machine-local user preferences
Layer 2:                    ~/projects/CLAUDE.md        — org-wide rules (optional)
Layer 3:                    [project-root]/AGENTS.md    — project constitution ← primary
Layer 4 (highest priority): [subdirectory]/AGENTS.md   — package/module overrides
```

Each layer overrides the one below it for its scope.

**Layer 1 — User level (`~/.claude/CLAUDE.md`):**
Your personal preferences. Applies to every project on this machine.
Set once per developer machine. Covers: coding style preferences, your always-on
rules, how you want Claude to communicate with you. Does not contain project specifics.

**Layer 2 — Org level (`~/projects/CLAUDE.md` or similar):**
Optional. Useful if you work on many projects in a single directory and want
shared org-wide rules without putting them in every project's AGENTS.md.
The Two-Bible model handles this differently — the Public Bible bootstrap generates
project AGENTS.md files that include universal rules. This layer is therefore
optional and rarely needed.

**Layer 3 — Project level (`[project-root]/AGENTS.md`):**
The primary instruction file. Generated by the Bible bootstrap. This is the
Project Bible's core file and conforms to the AGENTS.md open standard.
See `TWO_BIBLE_MODEL.md` for the full architecture.

**Layer 4 — Subdirectory level:**
For monorepos. Each package can have its own `AGENTS.md` that overrides the
root for that package's scope. The root AGENTS.md applies everywhere; a
`packages/api/AGENTS.md` adds or overrides rules for the API package only.

### MEMORY.md — Automatic Learning

Claude Code automatically maintains `~/.claude/MEMORY.md` (machine-local) and
can write to a project-level `MEMORY.md` when it learns something during a session.

**What MEMORY.md does:**
- Claude Code writes patterns it discovers during sessions
- It is read automatically at the start of relevant sessions
- It is machine-local — not committed to git, not shared with other agents
- It captures "what Claude learned in this project on this machine"

**How MEMORY.md relates to the scratchpad:**

| | MEMORY.md | docs/scratchpad/DAILY.md |
|---|---|---|
| Written by | Claude Code automatically | Human via /scratchpad:learn |
| Scope | Claude Code on this machine | All agents, all environments |
| Visibility | Local only, not in git | In project repo, private |
| Purpose | Claude remembers for itself | You decide what's worth promoting |
| Feeds | Future Claude Code sessions | Public Bible via export pipeline |

They are complementary, not competing. MEMORY.md is local memory for Claude.
The scratchpad is the cross-agent promotion pipeline.

**What to do with MEMORY.md in the scratchpad workflow:**

When running `/scratchpad:learn`, the agent should read MEMORY.md first —
it may have already captured the key learning. If MEMORY.md has it, the
scratchpad entry is still worth writing if the learning could be promoted
to the Public Bible. If it is purely local/project-specific, MEMORY.md
alone is sufficient.

**Bootstrap sets up the project-level file. You set up the global one.**

## Global User CLAUDE.md (`~/.claude/CLAUDE.md`)

Create this file once on each developer machine. It applies to every project.

```markdown
# Global Claude Code Instructions

## Identity
I am working with the Complete Development Handbook.
Handbook repo: https://github.com/nicolapitersky/Bible
Every project I work on has an AGENTS.md that I read before starting any task.

## My Always-On Rules
- Read AGENTS.md at the start of every new session
- Check .env.manifest before any cloud operation
- Never use `any` in TypeScript
- Never hardcode colours, spacing, or environment IDs
- Run `pnpm type-check && pnpm lint` before considering any task complete
- Write tests alongside code, not after

## My Preferred Style
- Concise, explicit code over clever code
- Named variables that describe purpose not content
- Error handling is not optional
- Comments explain why, not what

## When I Am Uncertain
I stop and ask. I do not guess on:
- Which environment I am operating in
- Cloud resource IDs
- Destructive operations
- Security decisions
```

## MCP Server Configuration

MCP (Model Context Protocol) servers extend Claude Code with direct access
to external services. Configure them once per project in `.claude/settings.json`
or globally in `~/.claude/settings.json`.

### Project `.claude/settings.json`

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/project"]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "${DATABASE_URL}"]
    },
    "brave-search": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-brave-search"],
      "env": {
        "BRAVE_API_KEY": "${BRAVE_API_KEY}"
      }
    }
  }
}
```

### Global `~/.claude/settings.json` (applies to all projects)

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "${HOME}/projects"]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],

        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}"

      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-brave-search"],
      "env": {
        "BRAVE_API_KEY": "${BRAVE_API_KEY}"
      }
    },
    "memory": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-memory"]
    }
  },
  "permissions": {
    "allow": [
      "Bash(git:*)",
      "Bash(pnpm:*)",
      "Bash(node:*)",
      "Bash(cat:*)",
      "Bash(ls:*)",
```

## Slash Commands (Custom)

Claude Code supports custom slash commands defined in `.claude/commands/`.
The bootstrap generates these for every project.

### `.claude/commands/check.md`
```markdown
Run the full quality gate on the current codebase:

1. pnpm type-check
2. pnpm lint --max-warnings=0
3. pnpm test:unit --passWithNoTests
4. node scripts/verify-env.js local
5. grep -r "console\.log" src/ --include="*.ts" --include="*.tsx" | grep -v "//.*console"

Report: number of errors in each category. Fix all before proceeding.
```

### `.claude/commands/feature.md`
```markdown
Start a new feature. I will provide the feature description.

Before writing any code:
1. Read AGENTS.md
2. Run `git status` — confirm branch and state
3. Run `git checkout -b feature/[slug-of-feature]`
4. Check docs/TOOL_REGISTRY.md — does a tool exist for any part of this?
5. Check src/components/ui/ — does a component exist for any UI needed?
6. State what you will build, what tools you will use, what tests you will write.
   Wait for my confirmation before proceeding.
```

### `.claude/commands/done.md`
```markdown
Complete the current task and write a handoff report.

1. Run pnpm type-check && pnpm lint && pnpm test:unit
2. Remove all console.log from changed files
3. Check for any hardcoded values that should be tokens or env vars
4. Update docs/TECH_DEBT.md for any compromise made
5. Write the handoff report to docs/AGENT_HANDOFF.md using the format in MULTI_AGENT.md
6. Stage all changes: git add -p (show me each change before staging)
7. Commit with the correct format: type(scope): description
```

### `.claude/commands/audit.md`
```markdown
Run a security audit of the current codebase.

Follow the Security Agent prompt from the handbook:
cat /tmp/handbook/prompts/PROMPT_LIBRARY.md | grep -A 80 "PROMPT 5"

Report all findings with severity. Do not fix — report only.
Create a GitHub issue for CRITICAL and HIGH findings.
```

### `.claude/commands/weekly.md`
```markdown
Run the weekly quality check.

Read docs/QUALITY_CHECKLIST.md and execute every item.
For each finding, report severity: CRITICAL | HIGH | MEDIUM | LOW
Create a GitHub issue titled "Weekly Quality Report — [today's date]" with all findings.
```

## Session Management

### Starting a Session (Claude Code)

Claude Code sessions lose context when you `/clear` or start a new terminal.
Always re-orient at the start of a session with changed context:

```bash
# The /init command re-reads AGENTS.md and .env.manifest
# Use it at the start of every new session
/init

# Or paste this manually:
# "Read AGENTS.md and .env.manifest. Confirm the project, environment, and branch."
```

### Multi-Turn Long Tasks

For tasks spanning many hours or multiple sessions:

1. Use `docs/AGENT_HANDOFF.md` as your persistent memory
2. At a natural stopping point: run `/done` (writes handoff report, commits)
3. Start the next session: run `/init` (re-reads AGENTS.md + last handoff)

This is the equivalent of a developer finishing their day and writing notes
for tomorrow — except the "developer" is the agent and "tomorrow" is the next session.

### Context Window Warning Signs

If Claude Code starts:
- Repeating questions it already asked
- Forgetting decisions made earlier in the session
- Making inconsistent choices

**Stop the session.** Run `/done` to commit and write a handoff. Start fresh.
Context window exhaustion is not recoverable within the session.

### Output Management for Long Responses

When Claude Code produces long output (large files, test results, build logs),
pipe it to a file rather than reading it inline — this preserves context window:

```bash
# Instead of reading large output directly
claude "run all tests and show me the results"

# Pipe long output to a file
claude "run all tests and write the full output to /tmp/test-results.txt, then summarise"
cat /tmp/test-results.txt  # Read separately if needed
```

This pattern keeps the context window lean for the actual reasoning work.

### Extended Thinking for Complex Problems

For architectural decisions, complex debugging, or multi-step analysis, enable
extended thinking explicitly:

```
"Think step by step about [complex problem]. Show your reasoning before proposing a solution."
```

Extended thinking uses more tokens but produces significantly better results for:
- Debugging non-obvious failures
- Designing data models or API shapes
- Evaluating architectural trade-offs
- Security analysis

Do not use it for mechanical tasks (adding a field, renaming a variable, writing a test).

### Parallel Task Strategy

Claude Code handles one task stream at a time. For genuinely parallel work
(multiple independent features or fixes), use Codex — it runs multiple tasks
simultaneously. See `stacks/codex.md` for the parallel batching pattern.

Within a single Claude Code session, prefer sequential focus over attempted
parallelism — context switches within a session degrade quality.

## Permissions Model (The Enforcement Layer)

This is the **enforcement layer** — it constrains what Claude Code can do
regardless of what AGENTS.md says. See `ENVIRONMENTS.md` for the conceptual
distinction between instruction and enforcement.

### The Three Settings Tiers

```
Managed/org policy        ← set by admin, cannot be overridden
  ↓ overrides
.claude/settings.json     ← project-level (committed to git)
  ↓ overrides
~/.claude/settings.json   ← user-level (machine-local, not committed)
```

For teams: put security-critical denylists in managed/org policy so no
project can accidentally or deliberately override them.

### permissions.deny — What Claude Code Must Never Do

The deny list blocks operations unconditionally. Always include these:

```json
{
  "permissions": {
    "allow": [
      "Bash(git status)",
      "Bash(git log:*)",
      "Bash(git diff:*)",
      "Bash(git add:*)",
      "Bash(git commit:*)",
      "Bash(pnpm install:*)",
      "Bash(pnpm run:*)",
      "Bash(node scripts/verify-env.js:*)",
      "Bash(cat:*)",
      "Bash(ls:*)",
      "Bash(find:*)",
      "Bash(grep:*)",
      "Bash(mkdir:*)",
      "Bash(cp:*)",
      "Bash(mv:*)"
    ],
    "deny": [
      "Bash(git push --force:*)",
      "Bash(git push origin main:*)",
      "Bash(rm -rf:*)",
      "Bash(firebase deploy:*)",
      "Bash(vercel deploy --prod:*)",
      "Bash(supabase db push:*)",
      "Bash(curl * | bash:*)",
      "Bash(wget * | bash:*)"
    ]
  }
}
```

### Read Protection for Secrets

Prevent Claude Code from reading sensitive files entirely:

```json
{
  "permissions": {
    "deny": [
      "Read(.env)",
      "Read(.env.local)",
      "Read(.env.production)",
      "Read(.env.staging)",
      "Read(*secret*)",
      "Read(*credential*)",
      "Read(*serviceAccountKey*)",
      "Read(*firebase-adminsdk*)"
    ]
  }
}
```

**Why this matters:** even if AGENTS.md says "never read .env files", Claude
Code might read them to answer a question about what variables are set. The
deny rule prevents this at the tool level — the instruction layer cannot
override it.

### disableBypassPermissionsMode

By default, Claude Code has a "bypass permissions" mode that can be enabled
interactively. For production projects and team settings, disable it:

```json
{
  "disableBypassPermissionsMode": true
}
```

Set this in managed/org policy for all team projects. Set it in
`.claude/settings.json` for solo projects working with production data.

**When to omit it:** during active development of new features where you
need maximum flexibility. Re-enable for any session touching production.

### Deny List Rationale

- `git push --force` → rewrites history, always disallowed
- `git push origin main` → production deploys must go through CI/CD
- `rm -rf` → irreversible, always ask
- `firebase deploy` → must run `verify-env.js` first via CI
- `vercel deploy --prod` → must go through CI/CD pipeline
- `supabase db push` → migrations require human review
- `curl/wget | bash` → code execution from internet without review
- Read(.env*) → secrets never visible to agent

## Hooks — Executable Governance

Hooks are the Claude Code implementation of the executable governance
principle described in `MULTI_AGENT.md`. They run shell commands before or
after tool use and can allow, deny, or rewrite the operation.

### Hook Configuration in settings.json

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write|Edit|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "node .claude/hooks/check-write-safety.js"
          }
        ]
      },
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "node .claude/hooks/check-bash-safety.js"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Write|Edit|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "node .claude/hooks/audit-log.js"
          }
        ]
      }
    ]
  }
}
```

### Hook Response Protocol

Hooks communicate via stdin/stdout:

- **Input (stdin):** JSON with `tool_name` and `tool_input`
- **Allow:** exit 0 with no output, or `{"allow": true}`
- **Deny:** `{"deny": true, "reason": "Human-readable explanation"}` — blocks the operation
- **Modify:** `{"updatedInput": {...}}` — proceeds with modified input
- **Inject context:** `{"contextInjection": "Warning: ..."}` — adds to agent context

A hook that crashes (non-zero exit, no valid JSON) blocks the operation by
default. Fail closed, not open.

### Hook: Environment ID Protection

The most critical hook — prevents hardcoded environment IDs from being written:

```javascript
#!/usr/bin/env node
// .claude/hooks/check-write-safety.js
// Blocks file writes that contain hardcoded environment IDs
// Cross-references .env.manifest for this project's known IDs

const fs   = require('fs');
const path = require('path');

async function main() {
  let input;
  try {
    const raw = fs.readFileSync('/dev/stdin', 'utf8');
    input = JSON.parse(raw);
  } catch {
    // Cannot parse input — allow (don't block on hook failure)
    process.exit(0);
  }

  const { tool_name, tool_input } = input;
  const content = tool_input?.new_contents ?? tool_input?.content ?? '';
  const filePath = tool_input?.path ?? tool_input?.file_path ?? '';

  // Load the environment manifest to get this project's known IDs
  const manifestPath = path.join(process.cwd(), '.env.manifest');
  if (!fs.existsSync(manifestPath)) {
    process.exit(0); // No manifest — cannot check, allow
  }

  let manifest;
  try {
    manifest = JSON.parse(fs.readFileSync(manifestPath, 'utf8'));
  } catch {
    process.exit(0); // Cannot parse manifest — allow
  }

  // Extract all known environment IDs from the manifest
  const knownIds = extractIds(manifest);
  if (knownIds.length === 0) process.exit(0);

  // Check if the content being written contains any known IDs
  const violations = knownIds.filter(id =>
    id.length > 6 && // Skip very short IDs that would false-positive
    content.includes(id) &&
    !isInEnvVarReference(content, id) // Allow process.env.VAR patterns
  );

  if (violations.length > 0) {
    const result = {
      deny: true,
      reason: `ENVIRONMENT ID PROTECTION: File write blocked.\n` +
              `Hardcoded environment ID(s) detected in ${filePath}:\n` +
              violations.map(id => `  - "${id}"`).join('\n') + '\n\n' +
              `These IDs must come from environment variables, not be hardcoded.\n` +
              `Reference .env.manifest and use process.env.VARIABLE_NAME instead.`
    };
    process.stdout.write(JSON.stringify(result));
    process.exit(0);
  }

  process.stdout.write(JSON.stringify({ allow: true }));
}

function extractIds(obj, ids = []) {
  if (typeof obj === 'string' && obj.length > 6) {
    ids.push(obj);
  } else if (obj && typeof obj === 'object') {
    if (obj._meta) {
      // Skip metadata fields
      const { _meta, ...rest } = obj;
      extractIds(rest, ids);
    } else {
      Object.values(obj).forEach(v => extractIds(v, ids));
    }
  }
  return ids;
}

function isInEnvVarReference(content, id) {
  // Allow patterns like: process.env.VAR, env.VAR, ${VAR}
  const safePatterns = [
    new RegExp(`process\\.env\\.[A-Z_]+.*${escapeRegex(id)}`),
    new RegExp(`\\$\\{[A-Z_]+\\}.*${escapeRegex(id)}`),
  ];
  return safePatterns.some(p => p.test(content));
}

function escapeRegex(str) {
  return str.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
}

main().catch(() => process.exit(0)); // Fail open on unexpected errors
```

### Hook: Secrets Detection

Prevents known secret patterns from being written to any file:

```javascript
#!/usr/bin/env node
// .claude/hooks/check-secrets.js
// Blocks file writes containing known secret patterns

const SECRET_PATTERNS = [
  { pattern: /sk_live_[a-zA-Z0-9]+/,        label: 'Stripe live secret key' },
  { pattern: /sk_test_[a-zA-Z0-9]+/,        label: 'Stripe test secret key' },
  { pattern: /whsec_[a-zA-Z0-9]+/,          label: 'Stripe webhook secret' },
  { pattern: /AIzaSy[a-zA-Z0-9_-]{33}/,     label: 'Google/Firebase API key' },
  { pattern: /service_role[^"'\s]*eyJ/,     label: 'Supabase service role key' },
  { pattern: /-----BEGIN (RSA )?PRIVATE KEY/, label: 'Private key' },
  { pattern: /ghp_[a-zA-Z0-9]{36}/,         label: 'GitHub personal access token' },
];

const fs = require('fs');

async function main() {
  let input;
  try {
    const raw = fs.readFileSync('/dev/stdin', 'utf8');
    input = JSON.parse(raw);
  } catch { process.exit(0); }

  const content = input?.tool_input?.new_contents ?? input?.tool_input?.content ?? '';
  const filePath = input?.tool_input?.path ?? '';

  // Never block writes to .env.example (template files are fine)
  if (filePath.endsWith('.env.example')) {
    process.stdout.write(JSON.stringify({ allow: true }));
    return;
  }

  const found = SECRET_PATTERNS.filter(({ pattern }) => pattern.test(content));

  if (found.length > 0) {
    process.stdout.write(JSON.stringify({
      deny: true,
      reason: `SECRETS PROTECTION: File write blocked.\n` +
              `Secret pattern(s) detected:\n` +
              found.map(f => `  - ${f.label}`).join('\n') + '\n\n' +
              `Secrets must never be written to source files.\n` +
              `Use environment variables and Secret Manager instead.`
    }));
    return;
  }

  process.stdout.write(JSON.stringify({ allow: true }));
}

main().catch(() => process.exit(0));
```

## Subagent Implementation (Claude Code)

This section implements the tool-agnostic Subagent Contract from `MULTI_AGENT.md`
using Claude Code's native subagent system. Read the contract first — this
section only covers the Claude-specific mechanism.

Reference: https://docs.anthropic.com/en/docs/claude-code/sub-agents

### Subagent Invocation Shape

In Claude Code, a subagent invocation has two parts:
1. A **subagent definition file** in `.claude/agents/*.md` (capabilities + constraints)
2. The **orchestrator's task prompt** (explicit scope + success criteria for this run)

Both are required for a safe contract: static constraints from frontmatter plus
run-specific scope from the orchestrator.

Reference invocation shape (verify against current Anthropic docs before use):

```json
{
  "task": "...",
  "disallowedTools": ["..."],
  "permissionMode": "default",
  "maxTurns": 15,
  "isolation": "worktree"
}
```

Persistent-memory variant:

```json
{
  "task": "...",
  "disallowedTools": ["..."],
  "permissionMode": "default",
  "maxTurns": 15,
  "isolation": "worktree",
  "memory": "project"
}
```

`memory` is a scope selector (`user | project | local`); omit it to disable
persistent memory.
If Anthropic docs differ, Anthropic docs are authoritative.

### Subagent Definition Format

Claude Code subagents are defined as markdown files with YAML frontmatter.
They live in `.claude/agents/` (project-scoped, committed to git) or
`~/.claude/agents/` (user-scoped, machine-local).

```markdown
---
name: test-writer
description: Writes and fixes unit tests. Use after code changes.
tools: Read, Glob, Grep, Write, Edit, Bash
disallowedTools: Agent
model: inherit
permissionMode: acceptEdits
maxTurns: 20
isolation: worktree
memory: project
---
You are a test writer. Your scope is limited to test files (`**/*.test.ts`,
`**/*.spec.ts`). Do not modify application source code. If you discover a
bug in the source that causes a test to fail, report it in your handoff
but do not fix it.

Follow the project's testing conventions in AGENTS.md.
When you finish, write a handoff report to docs/AGENT_HANDOFF.md.
```

Key frontmatter fields mapped to Subagent Contract elements:

| Contract element | Claude Code field | Notes |
|-----------------|-------------------|-------|
| Scope | Stated in the prompt body | No dedicated frontmatter field — be explicit in the markdown |
| Tool restrictions | `tools`, `disallowedTools` | `tools` is an allowlist; `disallowedTools` is a denylist |
| Turn limit | `maxTurns` | Integer — never omit |
| No nested delegation | Platform restriction + `disallowedTools: Agent` | Claude subagents do not delegate further; keep `Agent` disallowed as defence-in-depth |
| Isolation | `isolation: worktree` | Runs in a git worktree |
| Memory scope | `memory: user \| project \| local` | Or omit to disable persistent memory |

### maxTurns by Task Type

| Task type | maxTurns | Rationale |
|-----------|:--------:|-----------|
| Simple bounded (add a field, fix a test) | 10 | Few files, clear success criteria |
| Standard feature task | 20–30 | Multi-file, needs exploration |
| Complex investigation | 40 | Large codebase search, multiple hypotheses |

**Never omit maxTurns.** If a subagent runs out of turns, it should write its
progress to the handoff report. The orchestrator can then decide whether to
resume the subagent or reassign the remaining work.

### isolation: worktree

The `isolation: worktree` setting runs the subagent in a temporary git
worktree, preventing it from modifying the main working tree.

**Always use for:**
- Tasks that create branches
- Parallel subagents (prevents cross-contamination)
- Filesystem experiments or large refactors
- Any task touching production-related files

**Optional for:**
- Read-only analysis tasks (no writes to report results)
- Tasks that only read and produce a summary

**Never skip for:**
- Production-touching tasks
- Multiple subagents running simultaneously
- Tasks where rollback might be needed

### disallowedTools Examples

Claude Code tools reference: `Read`, `Write`, `Edit`, `MultiEdit`, `Bash`,
`Glob`, `Grep`, `Agent`, `WebSearch`, `AskUserQuestion`.

**"Write tests only" subagent:**
```yaml
tools: Read, Write, Edit, Glob, Grep, Bash
disallowedTools: Agent
```
Scope restriction in the prompt: "Only modify files matching `**/*.test.ts`
or `**/*.spec.ts`. Do not modify application source."
Tool restrictions alone do not enforce file-path boundaries; enforce those via
orchestrator scope plus hook/policy controls.

**"Read and summarise" subagent:**
```yaml
tools: Read, Glob, Grep
disallowedTools: Write, Edit, MultiEdit, Bash, Agent
```
Pure analysis — cannot modify anything.

**"CSS fixes only" subagent:**
```yaml
tools: Read, Write, Edit, Glob, Grep
disallowedTools: Bash, Agent
```
Scope restriction in the prompt: "Only modify `.css`, `.scss`, or
`tokens.json` files. Do not modify `.ts`, `.tsx`, or `.dart` files."

**Orchestrator (can spawn specific subagents):**
```yaml
tools: Read, Glob, Grep, Bash, Agent(test-writer, code-reviewer)
```
Restricts which subagents the orchestrator can spawn via `Agent(name, name)`.

### permissionMode Values

| Mode | Behaviour | When to use |
|------|-----------|-------------|
| `default` | Prompts user for each permission | Default for most tasks |
| `acceptEdits` | Auto-accepts file edits, prompts for bash | Standard feature work where edits are expected |
| `dontAsk` | Non-interactive mode; actions needing approval are denied instead of prompting | Background automation where denials are acceptable |
| `bypassPermissions` | Bypasses interactive permission prompts | Local experimentation only, never for production-touching work |
| `plan` | Read-only mode, no writes allowed | Research, analysis, codebase exploration |

**Recommendation:** Use `acceptEdits` for most write-capable subagents.
Use `plan` for analysis-only subagents. Use `dontAsk` only for background
tasks where the tools are already heavily restricted via `disallowedTools`.
Never use `bypassPermissions` in any project that touches production data.

### No Nested Delegation Enforcement

Claude subagents are not orchestrators. Keep `Agent` out of subagent capability
sets, and include `disallowedTools: Agent` where supported to enforce the same
rule at config level.

If a subagent determines it needs further delegation, it reports this in the
handoff report under "Next Recommended Actions" and returns control to the
orchestrator.

### Subagent Hooks

Subagents can have their own hooks in their frontmatter. The project's
existing hooks (environment ID protection, secrets detection) apply to
subagents automatically through `settings.json`. Subagent-specific hooks
are useful for additional constraints:

```yaml
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "./scripts/validate-readonly-query.sh"
```

## Rules Modularisation (`.claude/rules/`)

As projects grow, inline rules in `AGENTS.md` or `CLAUDE.md` become unwieldy.
The modular rules pattern moves domain-specific rules into separate files that
are loaded automatically by the IDE.

Reference: https://docs.anthropic.com/en/docs/claude-code/memory#organize-rules-with-clauderules

### How It Works

Claude Code automatically loads all `.md` files from `.claude/rules/` alongside
the main instruction files (`CLAUDE.md`, `AGENTS.md`). No explicit `@import` is
needed for files in this directory — they are loaded automatically.

For files **outside** `.claude/rules/`, use import lines in the exact format
`@path/to/import` in `CLAUDE.md` or `AGENTS.md`:

```markdown
# In CLAUDE.md or AGENTS.md:
@docs/api-conventions.md
@./.claude/rules/security.md
```

The `@` prefix is shorthand for "read this file and include its content as
additional instructions." Relative paths resolve from the file containing the
import line (not the process working directory). Imported files can recursively
import additional files up to five levels deep.

### Directory Convention

```
.claude/
├── CLAUDE.md                  ← Main project instructions (pointer to AGENTS.md)
├── rules/
│   ├── security.md            ← OWASP, auth, secrets, Firebase rules
│   ├── environment-safety.md  ← Env manifest verification, no wrong-project writes
│   ├── design-tokens.md       ← Token usage, no hardcoded values, component rules
│   ├── testing-conventions.md ← Test patterns, coverage, naming
│   └── api-design.md          ← REST/RPC conventions, error shapes, validation
├── agents/
│   └── ...
├── commands/
│   └── ...
└── settings.json
```

### Path-Specific Rules

Rules can be scoped to specific file paths using YAML frontmatter. The rule
only activates when Claude is working on files matching the pattern:

```markdown
---
paths:
  - "src/api/**/*.ts"
  - "src/api/**/*.tsx"
---
# API Development Rules

- All API endpoints must include input validation
- Use the standard error response format from `src/api/shared/errors.ts`
- Include OpenAPI documentation comments on every handler
```

Use glob syntax: `**/*.ts`, `src/**/*`, `*.md`, `src/components/*.tsx`.

### Inline vs Modular: When to Use Each

| Use inline (in AGENTS.md) | Use modular (.claude/rules/) |
|---------------------------|------------------------------|
| Project identity, env manifest | Domain-specific conventions |
| NEVER DO / ALWAYS DO lists | Path-scoped rules |
| Core architecture decisions | Rules shared across projects |
| Agent handoff protocol | Rules that change independently |
| Stack/tooling declarations | Rules that benefit from versioning |

**Rule of thumb:** If a rule applies to all agents in all contexts, keep it
inline. If a rule applies to a specific domain or file type, modularise it.

## Claude Code + Firebase Studio Together

Some projects use both Claude Code (for backend/logic) and Firebase Studio
(for Firebase-specific work like Security Rules, Functions, and Hosting).

**Division of responsibility:**
- Claude Code: application code, tests, CI/CD, non-Firebase work
- Firebase Studio: `firestore.rules`, `storage.rules`, Cloud Functions, Firebase Hosting config

**Handoff protocol between the two:**
1. Claude Code finishes its work and writes a handoff report
2. Firebase Studio agent reads the handoff report and AGENTS.md
3. Firebase Studio agent confirms `.env.manifest` Firebase IDs before any deploy

**Never have both agents working on Firebase configuration simultaneously.**
One agent owns Firebase config at a time.

## Prompt Patterns That Work Well

These patterns consistently produce better results across Claude Code sessions.
They apply equally to complex features, debugging, and code review.

### Explore Before Implementing

```
"Before writing any code, read the relevant files and tell me:
 1. What patterns are already in use for this type of thing
 2. Any risks or edge cases I should know about
 3. Your proposed approach
 Then wait for my confirmation before implementing."
```

Prevents agents from immediately writing code before understanding the codebase.

### Constrain the Scope Explicitly

```
"Make only the minimum change needed to achieve [X].
 Do not refactor anything that is not directly related.
 Do not change any tests that are currently passing.
 List exactly which files you will modify before you start."
```

Prevents scope creep — one of the most common agent failure modes.

### Verification Step

```
"After you are done, run:
 pnpm type-check && pnpm lint && pnpm test:unit
 Show me the output. Only tell me you are done if all three pass."
```

Agents often report tasks complete when they are not. Requiring a verification
run with visible output catches this before it becomes a handoff problem.

### Structured Debugging

```
"Do not fix anything yet. First:
 1. Reproduce the issue and confirm you can see it
 2. Identify the root cause (not a symptom)
 3. Propose a fix and explain why it addresses the root cause
 Then wait for my approval before making any changes."
```

Prevents agents from fixing symptoms, introducing regressions, or making
multiple speculative changes before understanding the actual problem.
