# TWO_BIBLE_MODEL.md — The Public Bible and the Project Bible

> Every developer using this handbook works with two layers simultaneously.
> Understanding the distinction is essential before starting any project.

---

## The Two Layers

### The Public Bible (this repository)

`https://github.com/nicolapitersky/Bible`

Universal. Public. Anonymised. Stack-agnostic governance.

Contains:
- Development principles that apply to every project
- Stack patterns (Next.js, Flutter, Supabase, Stripe, etc.)
- Security constitution
- Design system conventions
- Approved tool registry
- Quality loops and CI/CD templates
- Bootstrap and retrofit processes
- Agent constitition templates
- Self-updating via monthly automated agent + periodic learning promotions

Contains **nothing** that is project-specific, private, or sensitive.
No environment IDs. No secrets. No client names. No project names.

Anyone in the world can clone this repo and benefit from it.

---

### The Project Bible (inside each project repo)

`your-org/your-project/` — private, project-specific, extends the Public Bible.

Generated by the Bootstrap or Retrofit process. Contains everything the
Public Bible provides plus the project-specific layer on top:

```
docs/
  CODEBASE.md          ← How this specific project works
  TECH_DEBT.md         ← Compromises made in this project
  AGENT_HANDOFF.md     ← Handoff log between agent sessions
  MIGRATION_PLAN.md    ← Retrofit roadmap (if applicable)
  TOOL_REGISTRY.md     ← Approved tools for this project
  adr/                 ← Architecture decisions for this project
  scratchpad/          ← Daily learning capture (see below)
    DAILY.md
    EXPORT.md
    [session entries]

AGENTS.md              ← Project constitution (generated from Public Bible template
                          + project-specific values)
.env.manifest          ← Real environment IDs (NEVER in the Public Bible)
design-tokens/
  tokens.json          ← This project's specific colour and type choices
.claude/
  settings.json        ← MCP servers for this project's services
```

Private to the project owner. Never published. Contains real IDs, real
architecture decisions, real operational learnings.

## The Inheritance Relationship

The Project Bible **inherits** the Public Bible and **extends** it.

```
Public Bible (universal rules)
    ↓ bootstrap generates
Project Bible (project specifics on top)
    ↓ agents read both
Every task on this project
```

When the Public Bible updates (monthly agent, or learning promotions):
- New projects automatically get the latest — they clone from the current Public Bible
- Existing projects track which version they were bootstrapped against via
  `AGENTS.md` header and `.env.manifest._meta.handbook_version`
- When a project is ready to update, run Prompt 13 (Update AGENTS.md to current handbook version)

## The Learning Pipeline

Operational learnings flow upward — from project to Public Bible — but only
after anonymisation and human review.

```
Daily work across agents and environments
    ↓ /scratchpad:learn  (manual, end of session)
Raw session entries in docs/scratchpad/
    ↓ /scratchpad:summary  (manual, end of day)
Distilled DAILY.md — stays private in project
    ↓ /scratchpad:export  (manual, when ready)
Anonymised EXPORT.md — human reviews
    ↓ /bible:update  (manual, after review)
PR on Public Bible — reviewed before merge
```

**The invariant:** nothing project-specific ever reaches the Public Bible.
The project name, environment IDs, client context, specific incident details —
all stripped during the export step. Only the universal, transferable rule travels up.

## Why This Architecture

**For the project owner:** your project details stay private. Real Firebase project
IDs, real Supabase refs, real Stripe keys — none of this is ever near a public repo.
Your project-specific learnings and architecture decisions stay in your project.

**For the community:** the Public Bible accumulates universal knowledge from real
operational experience, anonymised and distilled. Every developer who clones it
benefits from patterns discovered in the field, not just patterns invented at a desk.

**For agents:** the distinction is clear. Agents reading `AGENTS.md` in a project
know that:
- Rules from the Public Bible are universal — apply everywhere
- Rules in the project's `AGENTS.md` MIGRATION STATUS section are project-specific
- The `docs/scratchpad/DAILY.md` contains recent learnings from this specific project
- Nothing in `AGENTS.md` or the scratchpad should go to the Public Bible without
  going through the export and review pipeline first

## The AGENTS.md Standard

The Project Bible's core file — `AGENTS.md` — conforms to the open AGENTS.md
standard stewarded by the **Linux Foundation's Agentic AI Foundation**.

**What this means:**

AGENTS.md is not a convention invented by this handbook. It is an explicitly
vendor-neutral open format supported across Codex (OpenAI), Cursor, Claude Code
(Anthropic), Windsurf, Jules (Google), and others. Over 60,000 open-source projects
use it. The Linux Foundation stewardship means it will evolve through open governance,
not at the discretion of any single vendor.

**How the Bible relates to the standard:**

The Bible sits *on top of* the AGENTS.md standard. It does not invent a rival
convention. It generates spec-compliant AGENTS.md files and adds a governance layer
on top — environment manifest safety, design system rules, scratchpad integration,
stack-specific safety rails.

Every tool that supports the AGENTS.md standard will read our generated files
correctly. Our extensions do not conflict with the standard — they extend it.

**Precedence rules (from the standard):**

- Repo-root `AGENTS.md` applies to the entire project
- Subdirectory `AGENTS.md` files override the root for their scope
- Tool-specific files (`.cursorrules`, `CLAUDE.md`) are derivatives — generated
  from `AGENTS.md` by `scripts/generate-ide-rules.js`
- The root `AGENTS.md` is the single source of truth; tool-specific files are
  read-only views of it

**Standard tracking:**

The quarterly review process monitors the AGENTS.md specification for changes.
When the standard evolves, `AGENTS_TEMPLATE.md` is updated to maintain compliance.
See `HANDBOOK_UPDATE.md` for the quarterly review process.

## The Broader Ecosystem

The Bible is one part of an emerging ecosystem. Understanding where it sits
prevents duplication and enables complementary use:

| Tool / Resource | What it is | Relationship to the Bible |
|-----------------|-----------|--------------------------|
| **AGENTS.md standard** | Vendor-neutral open format for agent instructions | Foundation the Bible builds on |
| **Packmind** | SaaS platform for centralising and distributing AI coding rules | Complementary — could distribute Bible-generated files across tools |
| **zebbern/claude-code-guide** | Comprehensive Claude Code power-user handbook | Source for Claude-specific patterns; Bible makes them cross-agent |
| **Anthropic cookbooks** | Official prompt engineering and API usage examples | Source for prompt patterns in stacks/ai-providers.md |
| **OpenAI cookbooks** | Official usage examples | Same |
| **MCP specification** | Protocol for agent tool use | Foundation for TOOLING.md MCP section |
| **Claude MEMORY.md** | Anthropic's auto-memory for Claude Code | Complements the scratchpad (local memory vs promotion pipeline) |

None of these are competitors. The Bible is the governance layer that integrates
across all of them and adds what none of them provide: environment safety, cross-agent
coordination, and a promotion pipeline from operational learning to public knowledge.
